# 协议第 70 轮（项目 145）实验结果与分析：阶段小结（第 50–69 轮）+ G-1 先量——最忙门以外的门口等待过线（2.40%，线 2.0%）

## 结论先行
- **阶段小结**：第 50–69 轮骨干网线 20 轮，按层分 6 类（见下表）。选路类开发全掉分；阻尼、余量、自动带宽三类“过开发、没确认”；门口端口类（FRR/LFA、BFD、make-before-break、抢占、软抢占、PCE 主动下发、过载位）先量全部不到线。**这些门口端口的先量，全部只在“最忙的那一扇门”上做。**
- **漏掉的一块**：用同一套门检测（门格 = 宽度 ≤ 2 的通道格），17 张图平均有 22–65 扇用到的门，最忙的那扇只占过门次数的 **7.04%**。第 43 轮账本“门口区等”7.32% 车·拍拆开：最忙门 **1.13%**，**别的门 6.19%**。
- **G-1 三步先量**（跳过线事先写定，提交 1cc47a6、4d0a007、2ec5108）：
  1. 别的门门口区等 **6.19%** 车·拍（线 2.0%）→ 过；
  2. 其中那一拍门格空着 **3.80%** → 过；
  3. 其中那台车接下来进的第一扇门就是这扇门 **2.40%** → 字面过（线 2.0%）。其中面前那格被别的车占着（排队）1.44%，没被挡 **0.95%**。
- 最忙门同口径只有 0.29%（与第 58–66 轮的小数字一致）。最高的是多门图：roomHA 4.75%、roomHE 4.61%、roomFF 4.03%、roomFD 3.86%。
- **判定**：按事先写定，下一轮写协议（RSVP-TE 逐跳接纳控制 / RFC 5712 软抢占搬到所有门）。但余量薄：门口规则真正能管的“没被挡”只有 0.95%，被挡的 1.44% 只有在队头那台也是白等时才算得上。协议第一步必须先只计数拆原因（规划器排的等 / 门规则 / 前车挡），再定机制。

## 为什么
以前讲的“门”多半指单车道割上的那扇（room250 的门 6），各轮先量都锁定“过门次数最多的门”。但地图上宽度 ≤ 2 的通道口很多（房间之间的小口），每任务平均过 3.6 扇，大部分过门发生在这些小口上。它们没有 LCAP 的门规则，也没有割名额，车在门口站着等多半是规划器（PIBT 排先后）让出来的或被前车堵着。门格空着、车又确实要过这扇门、却站着——这在骨干网里像“沿途每一跳都要做接纳控制，只盯着最堵的那条链路会漏掉一路上的排队”。

不确定之处：① “门口区”是离门 ≤ 3 步的房间格，房间小的图上一格可能同时靠近两扇门，只归给最近的那扇；② “没被挡”的 0.95% 里也有车在等对面过来的车（门格这一拍空，下一拍对面车进来），离线看不出，要只计数拆。

## 指向哪里
下一轮（第 71 轮）G-1 写协议：第一步只计数（不改行为）在 room250、roomHA、roomHE 上拆“门空着却在门口等”的原因：规划器排的等（下一拍对面有车要进 / 让给优先级更高的车）、执行器扣住、前车挡；按事先写定的线（某一类 ≥ 1.0% 车·拍）再选机制：规划器让给对面车 → RFC 5712 软抢占式“门空着时本侧先走”；前车挡 → 不做（排队）。
